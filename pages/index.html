rpi glyph 调整 · 真机 ANSI 逐格回放对比

每个面板都是 rpi-tui 组件输出的真实字节流，逐格转成 HTML： 网格第 N 列前面正好有 N 个字符，每个 cell 恒为 1ch，短行补足到面板宽度， 所以同一面板内所有行共用一条右边界。颜色是 theme.rs 真实的 Ansi256 索引换算成的十六进制值。不在渲染期做任何测量， 因此列位置不会漂移。

08note 折叠 · 连续变更只占一行，原地迭代

左栏 11 条 note 的真实渲染：22 行（含折行共 23 行），全部写进 transcript 并永久留在滚动缓冲区。右栏是 status_container 的单槽位——先 clear() 再 add_child(...)，与 state.rs:1535 show_retry 同一套机制。

改动前

  • add_child(Text) + add_child(Spacer(1))，一条 note = 2 行高
  • 105 个调用点全部指向 &ctx.chat / &state.chat_container
  • 长文案（那条 99 字符的 provider 提示）被 wrap_text_with_ansi 折成 2 行

改动后

  • 复用 status_container：clear() + 一条 Text
  • RunStatus::Working/Aborting/Idle 三个分支本就会 clear()，note 自动让位
  • 取消 Spacer(1)，行高 2 → 1

需要你拍板

  • 历史丢失。覆盖后旧 note 就没了。Default saved.／Could not save the default: … 这类带结果的提示被覆盖后，用户回翻时无法确认「刚才那次到底存没存上」。建议只折叠纯状态类 note。
  • 错误路径不该折叠。add_error_message 与一次性确认（Copied …、Default saved.）应继续写进 transcript。
  • 与 retry 抢槽位。show_retry 也写 status_container，note 在重试期间到达会顶掉 StatusIndicator::retry 的 spinner，反之亦然。
  • 并非严格一行。dock 宽度不足时长文案仍会折成 2 行。

生成方式

  • crates/rpi-cli/examples/glyph_capture.rs 调用真实组件 （AssistantMessageComponent、BashExecutionComponent、 Markdown、SearchBar、FooterComponent、 BrandLockup）与 interactive_tui/rendering.rs 的 note/error 助手，把原始字节流打到 stdout。
  • demo/ansi_grid.py 把 SGR 序列解析成逐格网格： 38;5;N 按 xterm 256 色表换算，38;2;r;g;b / 48;2;… 原样保留，1/22 映射到 font-weight。
  • 重新生成： cargo run -q -p rpi-cli --example glyph_capture > demo/_capture.txt 然后 python demo/build_glyph_demo.py。

与真机的差异（诚实说明）

  • 字形来自你系统的字体，与 Windows Terminal / WezTerm 不同；但列位置、 颜色索引、折行点由字节流决定，与真机一致。
  • ℹ ⏸ ✗ ⚠ ↳ ☐ ☒ 这些 EAW=N 但 Emoji=Yes 的符号，本页统一追加 U+FE0E（VS15，文本呈现） 并按 1 列排版，与组件输出的列数一致。如果你的终端把它们画成 2 列，那一处会差 1 列。
  • 01/02/03/05 的「改动后」与 08 的折叠版是用同一套组件与字符串渲染的 提案态（尚未写进源码），不是现有行为。
  • 未包含 alt-screen 外框、editor 输入框、footer 分隔线等布局元素；取样单元是 transcript 内的单条内容。
